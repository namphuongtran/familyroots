# Deployment

## Overview
Hybrid deployment: **backend** on Render (Docker), **web** on Vercel (Next.js),
**mobile** via Flutter build pipelines. Pulumi captures infra intent but some
resources remain scaffolded.

## Pipeline (as implemented in `.github/workflows/`)

| Component | Trigger | Mechanism |
|-----------|---------|-----------|
| backend | push to `main` (after `lint-and-test` passes) | `deploy` job posts `curl -f -s -S "$RENDER_DEPLOY_HOOK"` (`backend-ci.yml`); the job fails fast if the secret is missing |
| web | push to `main` (after build/test) | `npx vercel deploy --prod --token=$VERCEL_TOKEN` (`web-ci.yml`) |
| mobile | push to `[main, develop]` | Flutter build + test (`mobile-ci.yml`); **no deploy step** |
| infra | push to `[main, develop]` | `pulumi preview` on PR / `pulumi up` on `main` (`infra-ci.yml`) — currently a **no-op** because the Pulumi resources are stubs |
| repo hygiene | push to `[main, develop]` | gitleaks secret scan + no-committed-`.env` gate (`pr-checks.yml`) |
| db-backup | **schedule** (`cron "15 17 * * *"` = 00:15 Asia/Ho_Chi_Minh) + `workflow_dispatch` — not push | `pg_dump` → gzip → upload to Supabase Storage `backups` bucket + rotation (`db-backup.yml`); skips green with a `::notice::` if the 3 backup secrets aren't set — see [backup-restore.md](backup-restore.md) |

The first five workflows trigger on push to `[main, develop]`; `db-backup` is
schedule/dispatch-only and never runs on push.

**There is no staging gate today — `main` → production directly.** `develop` runs
CI (lint/test) but does not deploy. A dev → staging → prod promotion path is not yet
implemented; treat `main` as production.

## Render service (`infra/render/render.yaml`)
- Service `familyroots-api`, Docker (`backend/Dockerfile`), plan `starter`,
  region `singapore` (closest to Vietnam).
- DB `familyroots-db`, Postgres 18, plan `starter`, region `singapore`.
- Health check: `GET /health` (probes DB connectivity **and** migration status;
  returns 503 `degraded` if the DB is unreachable or not at head).
- **The image refuses to boot under `APP_ENV=production` unless the database is at
  head**, so a failed `preDeployCommand` cannot ship a schema-mismatched app: the
  deploy fails and the previous version keeps serving. The migration scripts ship
  inside the wheel for this reason — see `migrations.md` § "Boot-time migration
  gate" for the measurement of what happens when they do not.
- `APP_ENV=production`, `APP_SECRET_KEY` auto-generated by Render, `DATABASE_URL`
  injected `fromDatabase`, `ALLOWED_HOSTS` set to the JSON list
  `["familyroots-api.onrender.com"]` (the prod config fail-fast rejects a wildcard).

## Migrations relative to deploy
`preDeployCommand: alembic upgrade head` runs **before** each deploy goes live and
**blocks the deploy on failure** — a bad migration fails the release rather than
shipping a schema-mismatched app. See `migrations.md`.

## Rollback
- Backend: redeploy the previous green commit (Render keeps prior deploys — re-trigger
  the hook from that commit, or use Render's "Rollback" in the dashboard). If a
  migration shipped, roll the schema back first (`alembic downgrade <rev>`); note
  destructive migrations may not be cleanly reversible — prefer a forward fix.
- Web: Vercel keeps immutable deployments; promote a previous one in the dashboard.
