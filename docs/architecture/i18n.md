# Backend i18n

How the backend resolves a locale per request and renders localized strings —
error messages, kinship terms, and push-notification text — in vi/en/zh/fr.

## Locale resolution (request → ContextVar)

1. `LanguageMiddleware` (`backend/app/middleware/language_middleware.py`) reads the
   `Accept-Language` header, takes the first tag's first two characters
   (`"en-US,vi;q=0.9"` → `en`), and validates it against `SUPPORTED_LOCALES`.
2. Anything unsupported (or no header) falls back to **`vi`** — the platform default.
3. The result is stored in the `current_locale` ContextVar for the duration of the
   request and reset in a `finally` block afterwards.

`current_locale` and `SUPPORTED_LOCALES = {"vi", "en", "zh", "fr"}` live in
`backend/app/core/locale.py` — deliberately in `core`, not the middleware, so readers
(the translator service, exception handlers) never depend on the middleware layer:
the middleware *sets* the ContextVar; everything that renders text *reads* it.

## Translation mechanics — `t()`

`backend/app/services/translator.py`:

- `load_translations()` runs once at app startup (lifespan in `app/main.py`) and loads
  every `backend/app/i18n/*.json` file (flat `"key": "text"` dicts; currently 180 keys
  per locale, kept in lock-step across all four files).
- `t(key, *, locale=None, **kwargs)` resolves in this order:
  1. explicit `locale=` argument, else the `current_locale` ContextVar;
  2. the key in that locale's table, else **fallback to `vi`**;
  3. the raw key string if missing everywhere (last-resort, guarded by tests below).
  `kwargs` are interpolated with `str.format` (`t("notification.birthday.body", name="An", days=3)`).

The explicit `locale=` override exists for contexts with **no request ContextVar** —
chiefly the notification cron job, where `send_to_clan`
(`app/services/notification.py`) sends each recipient their own language from
`user_profiles.language` (synced from the JWT's `user_metadata.preferred_locale` by
`ensure_user_profile`, default `vi`).

## Key namespaces

| Prefix | Used for | Consumed by |
|---|---|---|
| `error.*` | Every structured-envelope error message (`error.<code>`) | Exception handlers in `app/core/exceptions.py` |
| `kinship.*` | Vietnamese kinship terms (ông nội, cô, cháu…) | `relationship_descriptor.py` tree/kinship read model |
| `notification.*` | FCM push title/body per event type (`notification.<event_type>.title/.body`) | Anniversary scheduler job |
| `auth.*`, `user.*`, `member.*`, `timeline.*`, `invitation.*`, `relationship.*` | Success/info messages on specific flows | Route handlers |

## The coverage test guard

`backend/tests/unit/test_i18n_coverage.py` turns "forgot the translation" into a CI failure:

- `test_every_error_code_has_a_vi_i18n_key` — regex-scans all of `app/` for codes passed
  to error constructors (`ValidationError("...")`, `AppError(...)`, etc.), plus the
  generic handler codes, and asserts each has an `error.<code>` entry in `vi.json`
  (the fallback locale — a miss there means users see a machine code).
- `test_all_locales_have_matching_error_keys` — asserts en/zh/fr each carry the full
  union of `error.*` keys, so no locale silently lags.

`tests/unit/test_translator_locale.py` pins the resolution contract itself: explicit
locale wins over the ContextVar, and an unknown locale falls back to vi text (not the
raw key).

## What is NOT translated

- **User-entered data**: person names, clan names, event titles, descriptions — stored
  and returned verbatim.
- **`HistoricalDate.display` and `.lunar`** (`app/schemas/historical_date.py`): these are
  free-text strings entered by users ("Đầu xuân Giáp Thìn", "15/01 ÂL") and pass through
  untouched. Clients must not expect them localized.
- Log lines and internal exceptions — English only.

## Adding a new message

1. Add the key to **all four** files: `backend/app/i18n/{vi,en,zh,fr}.json` (vi is
   mandatory — it is the fallback; the cross-locale test forces the other three for
   `error.*` keys, and convention keeps every namespace in lock-step).
2. Render it via `t("your.key", ...)` — never hardcode user-facing strings.
3. For a new **error code**, just raise it with the code string; the coverage test will
   fail until the `error.<code>` key exists.
4. Run `uv run pytest tests/unit/test_i18n_coverage.py -q` before pushing.
